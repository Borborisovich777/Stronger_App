# Previous weights and progression at workout start

## Research brief

Scope: Stronger users starting templates and logging sets, with immediate corrections in September 2026. The user reported an increase after one rep and clarified that increases should be applied before the next workout begins. The old algorithm reproducibly returned 62.5 kg after one completed 60 kg × 1 set and one matching historical set. Template construction also copied historical reps into the new plan, allowing a failed one-rep result to replace the saved rep target. Public tracker documentation separates previous performance from routine targets, while user feedback illustrates confusion when those concepts are combined. The product direction is to carry forward comparable weights, preserve the plan, and evaluate complete workloads only when constructing a new workout.

Source scan: current official Strong, Hevy and Everfit help; Bevel's public feedback board; Strong and Boostcamp Reddit discussions. Official docs describe product behavior, not the clinical validity of progression rules. [Everfit's autofill documentation](https://help.everfit.io/en/articles/14617776-client-app-autofill-weights-reps) supports explicit set-type matching; Stronger does not adopt its 1RM-based load inference. No analytics, support-ticket corpus, or user workout data was inspected. Public anecdotes establish plausible UX friction, not how often Stronger users encounter it.

## Implemented policy

- Every template start uses the latest completed comparable working-set weights, across all templates and blank workouts. Match exercise identity, tracking type and load convention. Additional sets reuse the final prior working-set weight. Saved template weight is only the fallback without history. Templates, History, set order and counts remain unchanged.
- Preserve numeric planned reps. New prepared templates carry their published upper-range progression target as structured data. Existing templates without that optional field use their saved numeric reps; the exercise actions menu exposes the progression goal.
- Progression is enabled by default and can be disabled in Settings without disabling previous-weight prefilling. It runs only at template start. Both latest comparable finished attempts must complete every working set at the current baseline loads and rep goal, with exactly matching working-set counts. A newer miss or incomplete attempt blocks an increase. Unrelated skipped exercises do not block a completed exercise.
- Reject single-rep plans/evidence, assistance, non-load tracking, zero load, invalid values, future evidence and recorded near-limit effort. Drops are not progression evidence.
- The step is 2.5 kg or 5 lb, limited to at most 10% of every working-set baseline and the app's load limit. These are conservative product bounds, not a readiness assessment or a medically validated prescription. Smaller equipment-specific increments require a separate design decision.
- Increased starting values are visible before the first set. A compact explanation lists adjustments; **Use previous weights** restores untouched prefilled values. User edits, set completion, added sets, resume and reload cannot trigger another increase.
- The old next-set-preview setting remains readable in backups for compatibility but has no effect. No saved records are rewritten or discarded.

Needs deeper research—program-specific deloads, exercise-specific readiness, and warm-up identification; these are not inferred from a single completed set.

## Validation

The production build and all 213 automated tests pass; ESLint and whitespace checks pass. Regression coverage includes single-rep results, incomplete workloads, rep-range maxima, per-set and repeated-row loads, future history, load modes, upper load bounds, backup compatibility and immutable inputs. Read-only review identified mismatches between the new prefill and the visible Previous column for repeated rows and future history; both were corrected with a shared lookup and regression tests. Final review found no remaining actionable defects.

Browser checks used disposable development preview data. Verified start-only increases, manual-edit-preserving undo, single-rep logging without new prompts, the progression-off fallback, new exercise/editor prefilling, prepared-template range goals and unchanged weights on resume. Checked the increase notice in the existing light and dark palettes at 320px, with no horizontal overflow. The development fixture is available at `?preview=progression`; it does not read or overwrite saved workouts.
